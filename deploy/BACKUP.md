# Резервные копии базы

Вся работа бота — в одном файле SQLite: `/opt/basketball-bot/data/bot.db`,
13 МБ, 44 таблицы.

## Что восстановимо и без копии, а что нет

| Данные | Откуда вернутся без копии |
|---|---|
| Протоколы игр, статистика игроков, `game_meta` | Скачаются из API лиг заново (`run_backfill.py`) |
| Опросы, анонсы, голоса, оплаты, посещаемость | Лежат и в Google-листах, бот их туда выкладывает |
| Лист «Игроки», «Конфиг» | Ведёт человек, база — только зеркало |
| **Составы фэнтези** (`fantasy_rosters`) | **Ничем.** Их собирали участники |
| **Очки по играм** (`fantasy_game_scores`) | **Ничем.** Фиксируются в момент игры и задним числом не пересчитываются |
| **История цен**, связки карточек | **Ничем** |

Последние три строки — вся причина, по которой копия нужна.

## Как снимается

`backup_db.py`, ночью в 03:20 МСК.

* Снимок делает `sqlite3.backup()`, а не `cp`. База в режиме WAL: копирование
  файла во время записи даёт битую копию без части свежих транзакций.
  Родной механизм идёт страницами и не требует останавливать бота.
* Каждую копию проверяем `PRAGMA integrity_check`. Копия, про которую
  неизвестно, целая ли она, хуже честного отсутствия.
* Архив пишется во временный файл и переименовывается. Умер процесс на
  середине — в папке не останется обрезка, который потом примут за годную копию.
* 13 МБ сжимаются до ~3,2 МБ.

## Сколько храним

7 последних ежедневных + воскресные за 8 недель — 14 копий, ~45 МБ.
Ежедневных хватает заметить свежую поломку; воскресные ловят ту, что тихо
жила месяц (все семь ежедневных были бы уже с ней).

Так же на локальном диске и на Диске: две площадки закрывают разные беды —
локальная спасает от «сломал сам», Диск от «умер сервер».

## Проверить, что копии есть

```bash
cd /opt/basketball-bot && ./venv/bin/python backup_db.py --list
```

## Восстановление

```bash
sudo systemctl stop basketball-bot
cd /opt/basketball-bot
cp data/bot.db data/bot.db.before-restore          # текущую не выбрасываем
gunzip -c backups/bot-db-2026-08-10.sqlite.gz > data/bot.db
./venv/bin/python -c "import sqlite3;print(sqlite3.connect('data/bot.db').execute('PRAGMA integrity_check').fetchone()[0])"
sudo chown botuser:botuser data/bot.db
sudo systemctl start basketball-bot
```

Файлы `bot.db-wal` и `bot.db-shm` от старой базы удалять не нужно — SQLite
разберётся сам, но если они мешают, их можно снести вместе с заменой файла.

После восстановления стоит один раз прогнать `run_backfill.py`: он дотянет
протоколы игр, случившихся после снятия копии.

## Google Диск

Копия уезжает в папку **«Basketball Bot — резервные копии»** тем же служебным
аккаунтом, что ведёт таблицы. Папка приватная: доступ открыт ровно одному
человеку — владельцу таблицы. Ссылками не делимся, в базе телефоны команды,
оплаты и telegram-id.

Настройки (в `.env`, все необязательные):

| Переменная | Смысл |
|---|---|
| `BACKUP_DRIVE_OWNER` | Кому открыть доступ к папке при её создании |
| `BACKUP_DRIVE_FOLDER_ID` | Заливать в готовую папку вместо своей |
| `BACKUP_DIR` | Куда класть локальные копии |
| `BACKUP_KEEP_DAILY`, `BACKUP_KEEP_WEEKLY` | Сколько поколений держать |

Разовое требование: в облачном проекте должен быть **включён Google Drive API**
(Sheets API уже включён, Drive — отдельный). Без него заливка отвечает 403, а
локальная копия при этом снимается как обычно, и в лист «Ошибки» падает запись.

Если Диск отвечает `storageQuotaExceeded` — у служебного аккаунта нет
собственного места. Тогда заводим папку в своём Диске руками, открываем к ней
доступ служебному аккаунту (Редактор) и прописываем её id в
`BACKUP_DRIVE_FOLDER_ID`.
