# Заготовка многокомандного бота

Отдельная песочница для нового продукта. **Нынешний бот сюда не заглядывает** —
ни один его модуль не импортирует `multi/`, поэтому что бы тут ни происходило,
команда этого не заметит.

## Что решено (11.08.2026)

**Один токен, база на каждую команду.** Не общая база с признаком команды.

Причина — в замерах нынешнего кода: 204 обращения к базе в 34 файлах. Провести
арендатора через все — недели работы, и любое забытое место означает молчаливый
показ чужих данных. База на команду меняет одну функцию: соединение открывает
файл текущей команды.

Плата за это — «текущую команду» надо аккуратно протаскивать через асинхронный
контекст, а фоновые задачи переписывать так, чтобы они явно шли по списку
команд. Этим и занимается `db.py`.

## Из чего состоит

| Файл | Что делает |
|---|---|
| `tenants.py` | Реестр команд: кто подключён, где его база, что оплачено |
| `db.py` | Текущая команда и её соединение; обход всех команд для фоновых задач |
| `onboarding.py` | Мастер подключения: шаги, вопросы, разбор ответов |
| `schema.py` | База одной команды: состав, опросы, игры, деньги |
| `membership.py` | Кто в какой команде — по личке чат не подскажет |
| `bot.py` | Телеграмный слой: свой токен, свой процесс |
| `tests.py` | Проверки — запускать `python3 multi/tests.py` |

## Главный предохранитель

`db.connection()` **падает**, если текущая команда не задана.

Это сделано намеренно и является главной защитой всей схемы. Забытый контекст
обязан ронять запрос с внятной ошибкой, а не молча открывать чью-то чужую базу.
Ошибка видна сразу, на первом же прогоне тестов; молчаливая утечка не видна
никогда — до жалобы клиента.

## Что даёт схема

**Удаление клиента — удаление файла.** `tenants.forget()` сносит и запись в
реестре, и базу. В договоре это сильный пункт, а в общей базе такое сделать
честно почти невозможно: строки клиента размазаны по сорока таблицам.

**Авария у одного не роняет остальных.** Битая база — беда одной команды.

**Выход к «токен на команду».** Если упрёмся в лимиты Телеграма, переезд стоит
копейки: данные уже разложены, менять надо только сопоставление «команда →
токен». Из общей базы обратно не разобрать.

## Мастер подключения

Правило одно: **человек не вводит ни одного идентификатора.** Чат бот узнаёт из
события «меня добавили в группу», название команды предлагает по названию
группы, состав принимает списком из заметок тренера.

Шаги: чат → название → тренировки → взносы → состав. Три последних можно
пропустить и задать потом — подключение не должно упираться в то, чего у
человека сейчас нет под рукой.

Разбор ответов терпимый к тому, как люди пишут: «ср, пт 20.30» и «среда и
пятница 20:30» — одно и то же. Требовать формат значит получить «не понял» на
первом же шаге, а это место, где подключение бросают.

Логика без Телеграма: шаги и разбор — обычные функции, проверяются без сети.
Состояние мастера в базе, а не в памяти: подключение делают один раз, и терять
его на середине из-за перезапуска — худшее первое впечатление.

## Запуск

```bash
MULTI_BOT_TOKEN=<токен НОВОГО бота> python3 -m multi.bot
```

**Свой токен обязателен.** Если переменной нет или в ней токен боевого бота —
процесс не стартует. Это не перестраховка: запустить новый код со старым
токеном значит подключить недоделанного бота к живой команде, и заметят это не
по логам, а по сообщениям в чате.

Как выглядит подключение живьём:

1. Тренер добавляет бота в чат команды → бот узнаёт `chat_id` из события и
   пишет тренеру в личку.
2. Пять вопросов в личке, три из них можно пропустить.
3. Команда заведена, в чат приходит подтверждение.
4. `/сюда` в нужной теме — так бот узнаёт id топика. Другого честного способа
   нет: в интерфейсе Телеграма этого номера просто не показывают.

## Чего здесь ещё нет

Меню команды (пока заглушка «скоро появится»), опросы и напоминания, слой
обслуживания (миграции по всем базам). Порядок и обоснование — в срезе v1–v4
(память проекта).
